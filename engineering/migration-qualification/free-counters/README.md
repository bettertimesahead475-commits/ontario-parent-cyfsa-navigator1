# Separate free Quick and Forensic counters — qualification

**Verdict: the ledger passes on A+B; the guarded A installer and optional old-worker settlement bridge pass locally; mixed-version Quick admission and operational release remain blocked.**
The release branch `dd02ef34` only grants free Quick Reviews. The implementation under test is the separately owned [free-trial candidate `71f5b68`](https://github.com/bettertimesahead475-commits/ontario-parent-cyfsa-navigator1/commit/71f5b6811d1c6e465286cc2836453a2c1b52a12d). It uses the existing `public.free_usage` and the same RPC signatures: `fq:<email hash>` and `ff:<email hash>` are independent one-use lanes. A UID with a positive legacy Quick count keeps the three-use ceiling on that same UID key; no rows are backfilled, reset or moved. A zero or absent legacy count takes the new Quick lane under this candidate. The split itself has no DDL dependency beyond A+B.

## Reproduce

Use local PostgreSQL server/client binaries (`pg_config`, `initdb`, `pg_ctl`, `psql`, `pg_dump`, `pg_restore`), the `en_US.UTF-8` locale, and Node 22 for the optional application tests. The harness creates its own temporary cluster with no TCP listener. Both the Unix socket and its enclosing directory are mode `0700`; all clients use that socket. Do not run it as root. `FREE_COUNTER_TEST_PORT` controls the socket filename suffix (default 54329).

```sh
git fetch origin refs/pull/164/head
git fetch origin devin/1795810799-free-trial-policy
git worktree add --detach ../free-trial-candidate 71f5b6811d1c6e465286cc2836453a2c1b52a12d
npm ci --ignore-scripts --prefix ../free-trial-candidate
bash engineering/migration-qualification/free-counters/qualify.sh ../free-trial-candidate
```

Omit the last argument to run the SQL-only portion. The harness exits nonzero on an unexpected result; `UNSAFE (historical control)` and `BLOCKED` lines are deliberate assertions of the old failures and the remaining Quick limitation. The candidate Vitest suite executes its TypeScript helpers against real PostgreSQL with a synthetic REST read adapter. It installs A in a separate scratch database; the shell/SQL portion exercises A+B and the bridge using the exact old/new RPC arguments. Neither path calls paid inference, Firebase, Supabase, or any deployed service.

The old Pages caller (`_free-credit-reservation.ts::reserveFreeScan`) supplies only raw UID. The old worker (`analyzer-queue-consumer.ts::finalizeReservation/releaseReservation`) also sends `owner_uid`; unlike direct Quick, queued work has a durable `analyzer_jobs` row containing the marker. The resolver uses the trusted job ID, owner, free-job mode and exact request digest to select the counter. Installing the bridge changes no job or counter data and adds no public API grants. The old worker does **not** implement the new candidate's provider-attempt cap, so settlement compatibility alone does not certify the full mixed-version Worker path.

To support mixed Pages rather than quiescing the old producer, the candidate owner would need to send both the verified UID and canonical key to a new reservation contract. A DB bridge could then bind them and serialize legacy/new claims under one lock, while preserving actual pre-cutover legacy allowances. That would still need a trusted initial link for any already-written split rows; the ledger alone cannot identify the account. No guessed match, global denial, counter rewrite, or second free-trial implementation was added.

## Read-only gate and recovery

1. Before a coordinated cutover, confirm the current Pages and Worker deployment IDs and their actual Supabase URL using read-only deployment metadata. Run [inspect.sql](inspect.sql) to check the catalog, table grants, RLS, invoker-mode RPCs and index readiness. Separately query `SELECT version, name FROM supabase_migrations.schema_migrations WHERE version IN ('20261127163256','20261127163309') ORDER BY version;` and compare the stored functions with #164 (allow for migration-tool comment stripping). In particular verify that `free_reconcile` has both the prefix comparison and the live-job exclusion. Missing history, unexpected fingerprints, role drift or wrong project means stop, not reapply.
2. For any approved database repair, confirm provider backup/PITR coverage and save the installed function definitions and grants before changing anything. Tested locally: `pg_dump -Fc` and `pg_restore --exit-on-error` to a **different** database (cluster roles already provisioned). The restored copy correctly omitted transactions committed after backup; replacing the source from that dump would erase them. Do not use A's down script or restore over the operational database.
3. Keep A+B unchanged if they match. Prefer the owner-approved worker-first cutover: verify the new worker, prevent old Pages from admitting free Quick requests while switching producers, and resume only on the new Pages build. On rollback, keep a split-aware worker until all split jobs settle; keep old Quick admission paused absent a qualified UID bridge. Do not reset or merge counters. The cutover mechanism and downtime are not measured here; a pause can interrupt new free starts, and drain time depends on outstanding jobs and retries.
4. After an approved cutover, rerun the read-only inventory and check only aggregate counts per known lane (no customer identifiers). If A was accidentally reapplied over B, the tested repair is **reapply verified B**, then repeat fingerprint and index checks. That preserves later rows but cannot undo effects from requests processed while the guard was missing. Reconcile any such transactions separately with owner approval.

If independently approved as a fallback, the settlement bridge must follow A+B and be verified before old consumers see split jobs. Save both installed settlement definitions with `pg_get_functiondef` and verify existing grants. The tested rollback restores those two definitions and drops only `free_queue_settlement_key(text,text)` in one transaction; no ledger rows are reverted. Do not remove it while old workers may still settle split markers. A raw A replay could remove the bridge's settlement bodies as well as B's guard; if the bridge is intended in that environment, reapply verified B **then** the bridge and recheck both.

No application code, existing migration file, production data, deployment or authoritative register was changed. The new SQL sits under `engineering/` for independent review and disposable qualification only.
