# Analyzer retry policy: inventory and unified behaviour

Scope: every path that starts an analysis or Deep Scan. Source of truth: `shared/analyzerRetryPolicy.ts`. Client runner:
`src/utils/analysisRetry.ts`. Server stages use the shared attempt budgets and transient statuses.

## Inconsistencies found (before this change, on `fix/analyzer-audit-findings` at a9bdaac6)

| Path | Before | Risk |
|---|---|---|
| Quick Review, single file (`/api/analyze`, stream) | Retried only a refusal before the stream started (up to 3). A stream-level `AI_RESPONSE_INVALID` was not retried. A 429 was never retried. A dropped connection followed the job, correctly. | Same failure treated differently by stream and JSON replies |
| Forensic In-Depth | Same path as Quick Review (`mode: "full"`). | Same as above |
| Bulk processing (`/api/analyze`, JSON) | Up to 3 attempts, 1.5 s backoff growing ×1.5 to 10 s. Retried every error except `AI_RESPONSE_INVALID`, including rate limits (no wait). Sent **no analysis id**. A network failure re-sent a new analysis. | **Double charge:** a retry after a lost response started a second paid analysis with a new idempotency key |
| Deep Scan (`/api/deep-scan`) | No automatic retry. Sent **no analysis id**. The report was not saved as a job, so a dropped connection lost a charged result. | Retry starts another paid scan; a completed scan cannot be recovered |
| Server provider call (`generateContentWithFallback`) | Retries 429, 500, 502, 503, 529 and connection failures; two attempts. 408 and 504 not retried. | Budgets and status lists defined in several places |
| Server sections and Deep Scan sections | Two attempts each; Deep Scan had its own constant. | Duplicated constants |
| Client analysis id | `"req_" + Date.now() + "_" + random.substring(2, 9)` could be shorter than the server accepts, so the server replaced it and the retry protection was lost. | Silent loss of idempotency |

## Unified behaviour (after this change)

- One analysis id per analysis, reused by every attempt, on every path (`X-Analysis-Id`). Enforced by a guard test that every
  `/api/analyze` and `/api/deep-scan` request in the analyzer component carries it.
- Ids are generated by `newAnalysisJobId()`, which always yields a valid id.
- Failure classification (`classifyFailure`):
  - Cancelled: stop.
  - Dropped connection or stream interruption: **recover the saved job**; never resubmit.
  - 409 `ANALYSIS_IN_PROGRESS` or `ANALYSIS_ALREADY_COMPLETED`: recover.
  - 404 `JOB_NOT_FOUND`: the server never recorded the analysis, so resubmitting is safe.
  - 429 or `AI_RATE_LIMITED`: wait 30 s, then retry (2 retries).
  - `AI_RESPONSE_INVALID` that is retryable: one retry. A failed analysis releases its credit on the server.
  - Temporary server or provider statuses (408, 500, 502, 503, 504, 529): up to 2 retries with 2 s and 4 s waits.
  - Anything the server marks not retryable (sign-in, usage limit, forensic upgrade, unreadable document, refusal): stop.
- Retry budgets are per kind, excluding the first attempt, with an overall cap of 6 requests.
- Deep Scan now saves its result as a job under the analysis id, and records a failure on that job. A retry, or a
  reconnect after a dropped connection, recovers the saved report instead of running the scan again.

## Behaviour changes a reviewer should know about

- Single-file analyses now retry one server-reported invalid output automatically, as bulk processing already did.
  Before, the parent was asked to press Retry.
- Single-file analyses wait 30 s after a rate limit, then retry once, and show the wait in progress.
- Bulk processing and Deep Scan now recover a running analysis after a dropped connection, instead of starting it again.

## Not changed (documented)

- The OCR call (`generateGeminiContentWithRetry`, three attempts across models) keeps its own retry: it is provider-specific
  and does not create an analysis or charge.
- Deep Scan sections run without the shared deadline that the sectioned pipeline uses (`aiDeadlineAt`). A slow scan can still
  exceed the function limit. Recorded as a remaining risk.
- The server's generic fallback error (`INTERNAL_ANALYSIS_ERROR`, retryable) is treated as temporary, so an unexpected
  server bug is retried, up to the budget.
